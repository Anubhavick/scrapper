# 21 — CI: pytest + alembic check on every push/PR

Flagged as a gap review found: there was no `.github/workflows` at all —
`uv run pytest` only ran when a human remembered to run it locally. For a
system that now sends real email (a real send happened 2026-09-13), a
regression slipping through unnoticed has real consequences: a broken
suppression check, a bad send, a cap-logic regression. No automated gate
existed to catch any of that before it reached `main`.

## What was built

- **`.github/workflows/ci.yml`** — a single `test` job, triggered on
  push to `main` and on every pull request:
  1. A real `postgres:16` **service container** (not SQLite) — needed
     both because `db/models.py` uses JSONB/UUID columns SQLite can't
     represent, and because `alembic check` (below) needs a real
     database to diff against.
  2. `uv` installed via the official install script (not the
     `astral-sh/setup-uv` marketplace action — avoided deliberately
     since this session has no way to verify which action version is
     current; the install script is the same one CLAUDE.md's own setup
     instructions implicitly rely on via `uv sync`).
  3. `uv python install` (reads `.python-version`, already pinned to
     3.12), `uv sync` (reads the committed `uv.lock`).
  4. `uv run pytest` — the existing suite, which needs no DB connection
     at all today (confirmed: nothing in `tests/` imports
     `db.session.get_engine`/`session_scope`, per CLAUDE.md's note that
     the DB-touching modules aren't covered by this suite yet — see
     ROADMAP.md item 12).
  5. `uv run alembic upgrade head` against the fresh service-container
     Postgres, then `uv run alembic check` — the exact two commands
     CLAUDE.md's own "day to day" command list already documents, now
     run automatically instead of only when a human remembers to.

## Verification

Ran the individual commands this workflow chains together against a
real, already-running dockerized Postgres 16 (`docker compose up -d` +
`uv run alembic upgrade head`, both already current from earlier
verification work this session):

- `uv run alembic check` → `No new upgrade operations detected.` —
  confirms `db/models.py` and the migration history agree, which is
  exactly what this job's final step checks.
- `uv run pytest` → 263/263 passing, confirming the suite runs clean
  with no DB dependency.

**Not verified**: the workflow file itself was not run through an actual
GitHub Actions runner — doing that requires pushing a commit to GitHub,
which this session did not do on its own initiative (see CLAUDE.md's
standing rule on human-in-the-loop for anything visible to others).
GitHub's `ubuntu-latest` runner environment could in principle differ
from local Docker in some way this didn't surface (network egress to
`astral.sh` during the install step, most plausibly). The right next
verification step is watching the first real push/PR trigger this
workflow and fixing anything that doesn't translate, not assuming it's
correct sight-unseen.

## Not done here

- **No lint/type-check step.** This only runs the existing test suite
  and the migration-drift check — nothing enforces formatting or type
  annotations. Not requested, not added speculatively.
- **No coverage reporting.** Given ROADMAP.md item 12 (the DB-touching
  half of the codebase has zero test coverage by construction), a
  coverage percentage right now would be actively misleading — worth
  revisiting once that gap is closed, not before.
