# 18 — `/mailboxes` health page

ROADMAP.md item 6: "Mailbox health/reputation has no visibility beyond
token validity. No way to tell from inside the app if Gmail has started
flagging a sending account as spam."

## What's actually buildable here, and what isn't

A real spam-reputation signal (deliverability/reputation data the way
Google's Postmaster Tools exposes it) isn't reachable through the
`gmail.send` scope this system holds, and getting a broader signal would
mean the same restricted-scope/CASA path step 7 is already deliberately
deferred on (ROADMAP.md, 2026-09-13) — not solved here, and not
pretended to be solved here. What *is* buildable today, with zero new
scopes or CASA review:

- **Token validity** — already existed (`send/oauth.py`'s
  `validate_token_health()`, used by the orchestration loop's preflight
  check, docs/16) but had no visible surface outside log output.
- **Send volume against the daily cap** — already computable
  (`db/repository.count_sent_today()`), also previously invisible
  outside a preview run.
- **Whether the mailbox's last real send attempt actually succeeded** —
  genuinely new: nothing persisted this before. A mailbox that Gmail
  starts rejecting sends from (rate-limited, flagged, or otherwise) will
  show up here as repeated real failures, which is the closest signal to
  "reputation trouble" actually available without new scopes.

## What was built

- **`src/leadgen/db/models.py`** — `Mailbox` gained
  `last_send_error`/`last_send_error_at` (both nullable). Point-in-time
  state, not a history log and not a counter needing a reset job (the
  exact thing CLAUDE.md's schema-decisions note already warns against
  for this table) — each real send attempt overwrites them: cleared on
  success, set on failure. Migration `7a0fe0a19027`, autogenerated and
  applied; `alembic check` confirms no drift.
- **`src/leadgen/db/orchestration.py`** — `run_approved_messages()`'s
  `on_sent` now also clears `last_send_error`/`last_send_error_at` on
  the job's mailbox (a real success is the clearest evidence a mailbox
  is currently healthy); `on_error` now sets both. Both gated on `not
  dry_run` — `dry_run`'s faked Gmail call can't fail in a way that means
  anything about the mailbox's real-world health, so dry-run activity
  never touches these fields (mirrors `on_sent`'s existing dry-run gate
  for `gmail_message_id`).
- **`src/leadgen/api/mailboxes.py`** (new) — `/mailboxes`, read-only,
  listing every registered mailbox (active and inactive) with: a live
  token-health badge (a real call to Google's token endpoint made fresh
  on every page load, deliberately not cached — this is an occasionally
  viewed admin page, not a hot path, and a stale "looked fine 10 minutes
  ago" defeats the point), today's sent count against the daily cap
  (color-coded: fine / near cap / at cap), and the last real send error
  with its timestamp, or "none since last success." One mailbox's check
  failing (missing OAuth config, a corrupted stored token, a transient
  network error reaching Google) can't take down the page for every
  other mailbox — `_check_token_health()` catches broadly around just
  that call and renders "unknown" instead of 500ing the whole page.
- **`api/nav.py`** — added a "Mailboxes" link; **`api/review.py`** —
  mounted the new router, covered by the same app-level
  `dependencies=[Depends(require_auth)]` (docs/17) as every other page,
  no separate opt-in needed.

## Tests

`tests/test_mailboxes_api.py` (new, 9 tests): pure tests for the
rendering helpers (`_token_health_badge`, `_cap_badge`,
`_last_error_html`) built directly against `Mailbox` model instances,
the same pattern `test_review_api.py`'s `test_business_row_dict_matches_csv_row_shape`
already established for testing a DB-model-shaped pure function without
a real session. Covers: unknown/healthy/unhealthy token badges (with the
failure reason surfaced), cap badges at three thresholds (comfortable,
near, at-cap), no-error vs. a real error-with-timestamp, and HTML
escaping of the stored error text (it's operator-facing free text from
Google, not sanitized upstream — confirmed `<script>` renders as
`&lt;script&gt;`, not live markup).

`uv run pytest`: 226/226 passing (217 before this batch, +9 new).

## Verification against the real running server

`api/mailboxes.py` is excluded from the automated suite for the usual
JSONB/UUID-vs-SQLite reason (same as every other DB-touching `api/`
module) and makes a real external call besides — verified by hand
against the real running server (`scripts/dev.sh up`):

- `GET /mailboxes` with no credentials → `401` (still covered by
  docs/17's auth, no separate opt-in needed — confirmed, not assumed).
- With correct credentials → `200`, and the one real registered mailbox
  (`anubhav.ickk@gmail.com`) rendered with a genuine live "token ok"
  (an actual successful refresh-grant call to Google made during this
  request), `1/50` sent today (matching the one real send from this
  session, correctly color-coded green), and "none since last success"
  (accurate — never has a real send attempt failed for this mailbox).
- Inserted a disposable mailbox with a deliberately garbage refresh
  token and a pre-set `last_send_error`, hit the real page again:
  rendered "token dead: <Google's real `invalid_grant` response>" and
  the stored error text, both correctly — then deleted the disposable
  row and confirmed only the one real mailbox remains.
- Nav bar link confirmed present and pointing at `/mailboxes` in the
  real rendered page.

**Not independently verified: `on_sent`/`on_error` actually firing from
inside a real `--live` orchestration run.** Exercising that would
require a real Gmail send (`dry_run=False`), which this session will not
trigger on its own initiative regardless of what it's verifying — per
the hard rule that no live send happens without a human's explicit,
separate confirmation. What *is* verified: the columns read/write/render
correctly against real Postgres (above), and the two new lines in
`on_sent`/`on_error` are structurally identical to the existing,
already-verified `session.get(...)` + attribute-set + `commit()` idiom
one function up (`_reserve_fn`'s handling of `Message`) — low-risk by
construction, but the real-send path itself stays unverified the same
way MANUAL.md already flags `--live` as unverified end-to-end. Worth
confirming for real the next time a real campaign is sent.

## Not done here, still real gaps

- **No real reputation/deliverability signal** — see "what isn't
  buildable" above. Revisit only if/when step 7's restricted scopes (or
  Postmaster Tools, which needs a verified domain, not applicable to
  personal Gmail accounts) become available.
- **No history, just current state.** A mailbox that failed five times
  yesterday and succeeded once this morning shows as healthy — matches
  the "no counter/history without solving the reset/retention question
  first" caution already applied to `mailboxes.daily_cap` elsewhere in
  this schema; revisit if a real incident shows this isn't enough.
- **No alerting.** This is a page a human has to remember to check, not
  a notification. Fine for the current "one person supervises every
  send" posture; would need real thought (who gets paged, on what
  threshold) before this runs unattended.
